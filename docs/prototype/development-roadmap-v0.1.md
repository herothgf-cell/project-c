## 0. 프로토타입의 성공 정의

> 플레이어가 기억을 삭제해 ‘다른 과거를 믿게 되는’ 원리를 짧게 이해하고, P02에서 삭제할 것뿐 아니라 **언제 지울지** 고민해 행동 변화를 계획한다.

**대표 지표(목표, 달성 주장 아님):**
- 첫 설명 후 10초 안에 조작 목표를 자기 말로 설명하는가.
- P01은 규칙 학습, P02는 손실·시점의 ‘아하’, P03은 기억 소유 독립 이해에 성공하는가.
- 잘못 배송했을 때 이유를 행동 로그/근거에서 추적할 수 있는가.
- 해결 이후 다른 퍼즐도 풀고 싶다는 자발적 반응이 있는가.

초기 검증 규모 **3개 방 + 1개 최종 이야기 선택(2종 짧은 엔딩)**. 퍼즐 수나 세계를 검증 전 확대하지 않는다.

## 2. M1에서 최종 결정할 기술 스택(권고)

**1순위 검토:** Godot 4 2D + GDScript. PC 개발/테스트가 주인 환경에 적절하고, 성공 시 웹 내보내기 및 모바일 브라우저 확인. C# 선택은 첫 웹 프로토타입에서 우선하지 않음.

**대안:** 브라우저 제작/빠른 링크 공유에 높은 우선순위가 생기면 Phaser + TypeScript 등 웹 중심 구성을 다시 검토. Unity는 기존 경험/자산 활용이 확실할 때 비교. **엔진을 v0.3 내용만으로 확정 처리하지 않음.**

기술적 격리 권고:
- `game/logic/`: 카드·사실·근거 선택·턴 커밋·Undo의 결정론적 모델
- `game/content/`: P01~P03 데이터(예: JSON 또는 Godot Resource 중 M1에서 선정)
- `game/ui/`: 기억 패널, 실제 세계, 행동 기록, 스토리
- `game/storage/`: 퍼즐 진행/마지막 보고 결과 저장
- `tests/`: 순수 규칙 시나리오 + 필요 시 자동화된 엔진 실행 검증
- `.github/workflows/`: 웹 빌드/배포(게임이 실제 실행된 후 추가)

작업 방식: 가능하면 **상태 처리와 UI를 분리**. 콘텐츠 데이터에 카드의 보여줄 문장과 내부 의미(facts)를 함께 저장하되, 동작 판단을 자연어 문장 파싱에 의존하지 않는다.

## 3. 규칙 테스트 시나리오 — M2/M3 필수

| ID | 준비 상태 | 조작 | 기대 결과 |
|---|---|---|---|
| T01 | P01 기본 | A-02 삭제 | A 현재 판단 W; 근거 A-01 |
| T02 | P01 기본 | A-01·A-02 삭제 | Unknown; 실행 시 대기, 성공 아님 |
| T03 | P01 기본 | A-01 삭제 후 실행 | E 오배송, 실패 |
| T04 | P02 기본 | A-13 삭제→실행→A-12 삭제→실행 | 첫 배송 민아 W, 두 번째 준 E, 성공 |
| T05 | P02 기본 | A-13·A-12 삭제→실행 | 민아 Unknown, 대기 |
| T06 | P02 기본 | A-13 삭제→실행→실행 | 민아 W 배송 후 준 N 오배송, 실패 |
| T07 | P03 기본 | A-22만 삭제→실행 | A W, B E 오배송, 실패 |
| T08 | P03 기본 | A-22·B-22 삭제→실행 | 두 배송 W, 성공 |
| T09 | P03 기본 | A-22와 B의 카드 전부 삭제→실행 | A W 배송, B Unknown 대기, 성공 아님 |
| T10 | P02 기본 | A-13 삭제→실행→Undo→Undo | 1회 Undo 시 첫 배송 이전, 2회 Undo 시 A-13 복원; 초기 상태와 동일 |
| T11 | 임의 방 | 여러 삭제·실행 후 Restart | 그 방 초기 상태와 같고 Undo 기록 비움 |
| T12 | P03 | A 카드만 삭제 | B 카드/판단 변화 없음 |
| T13 | 모든 방 성공 후 | 공개/내부 보관 선택 각각 | 엔딩/저장 플래그만 달라지고 배송 완료 사실 불변 |
| T14 | 같은 초기 상태·조작열 | 복수 실행 | 매번 동일 상태/로그 |

각 테스트는 성공/실패뿐 아니라 **카드·근거·배송 순번·로그·Undo 스냅샷**도 확인한다. 문제 풀이 재미/난이도는 자동 테스트로 대체할 수 없다.

## 4. 프로토타입 주요 재미 목표와 확인 방법

| 재미 목표 | 테스트 질문 | 실패 신호 | 대응 원칙 |
|---|---|---|---|
| 믿음이 바뀌는 즐거움 | P01 최근 카드를 지운 이유를 설명할 수 있나? | ‘삭제=정답 버튼’이라고만 설명 | 최신 근거 표시/전후 판단 UI 강화 |
| 사건 전체 삭제의 부담 | P02에서 A-12가 두 사람에게 미치는 효과를 이해했나? | 준에 관한 정보 손실을 인식하지 못함 | 카드 내 여러 사실의 인물 연결 강조 |
| 행동 순서 설계 | P02에서 민아 먼저 배송해야 하는 이유를 말하나? | 무작정 카드 전부 삭제해보고 반복 | 첫 배송 완료 상태와 판단 변화 강조 |
| 정보의 독립성 | P03에서 A 원본 삭제가 B에 안 미치는 이유를 말하나? | 같은 카드가 복제됐다고 혼동 | 출처/소유자 별도 배지 |
| 공정한 실패 | 잘못 배송된 이유를 납득하나? | 규칙을 모르겠다는 반응 | 행동 로그와 실제 위치 병기 |
| 이야기 동기 | 마지막 보고 선택이 상황과 연결된다고 느끼나? | 갑작스러운 임의 선택처럼 느껴짐 | 도입과 결과에 감사 기록 복선 제공 |

## 5. 검토 우선순위 및 변경 제한

- **P0:** 규칙 모순/도달 불가능 해법, Undo 오류, 카드 소유자 혼동, 실패 이유 불명확.
- **P1:** P02 난이도·학습곡선, P03 반복감, 저장/이어하기, 브라우저 실행 문제.
- **P2:** 그래픽 완성도, 세부 사운드, 부가 애니메이션.
- 스테이지 확대·NPC 이동·대화 중 기억 전달·메타 성장·상업 모델·부분 유료화는 프로토타입 통과 전 도입 금지(별도 합의가 있으면 재검토).
- ‘완성’은 코드가 존재하는 상태가 아니라 **테스트 통과 + 실제 실행 + 사람의 조작/재미 검증 근거 확보**로 판단.

## 6. GitHub/Codex 작업 규칙(권고)

1. `main`에는 검토된 변경만 병합. 구현은 `feat/*` 등 작업 브랜치에서 PR 단위 진행.
2. PR마다 목적, 영향 파일, 실행 명령, 자동 테스트 결과, 직접 확인이 필요한 항목을 기록.
3. 컨텐츠 변경 시 관련 퍼즐의 성공·실패·대기 경로도 업데이트. 이전 기획서는 덮어쓰지 않고 버전 파일로 유지.
4. Codex 요청은 **한 번에 한 마일스톤의 하위 작업**만. 예: “M2-1 기억 판단 및 테스트만 구현”.
5. 웹 배포는 M5. `main` 반영→빌드→GitHub Pages 배포를 자동화할 수 있으나 최초 설정 및 엔진 웹 내보내기 검증 필요.
6. 이번 문서 푸시는 **개발·배포 완료를 뜻하지 않는다**. M0 기획 리뷰 단계만 반영한다.
